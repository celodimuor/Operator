## When to write an ADR

| Trigger | Example |
|---|---|
| Architectural choice with alternatives | storage model, runtime, protocol |
| New dependency (gem, npm package, service) | adding a gem requires an ADR and a licence check |
| New core touch or touch beyond budget | any edit outside `operator/` not already in `upstream-touches.yml` |
| Exception to a standard or another ADR | a second `routes.prepend` block |
| Reversal of an accepted ADR | write a new ADR that supersedes it |

## How to write one

1. Copy the structure of an existing ADR. Next number = highest number + 1; numbers are never reused.
2. File name `NNNN-kebab-title.md`.
3. Frontmatter: `status` (`proposed` \| `accepted` \| `rejected` \| `deprecated` \| `superseded by NNNN`), `date` (ISO), `deciders`.
4. Sections in order: Context and Problem Statement; Decision Drivers; Considered Options (at least two real options); Decision Outcome with Consequences (Good / Bad); Confirmation (the CI job or check that proves compliance).
5. Tables over prose. Name real paths, constants and CI jobs; the references spec fails on names that do not exist (mark not-yet-built paths as planned).
6. Land the ADR in the same PR as the change it governs. Add a row to this index.
7. Never edit the decision of an accepted ADR; supersede it and set the old one's status to `superseded by NNNN`.
